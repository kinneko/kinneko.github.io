　2年くらい放置していたら、ちょっと支払いがバカにならないくらいの金額になってきたので、コスト圧縮でS3のオブジェクトを削除する。

　とはいえS3分は、$1/月くらいなのだけどw

　Log Archveのアカウントに入ってS3のバケットの中身を空にする。自動作成されているバケットは２つ。 「aws-controltower-logs-XXXXXXXXXXXX-ap-northeast-1」と「aws-controltower-s3-access-logs-XXXXXXXXXXXX-ap-northeast-1 」がある。

![](/2024-10-18/8727020-01.png)

　ストレージレンズで見るとこんな感じ。結構たまっているものなのね。

![](/2024-10-18/8727020-02.png)

　中を見ながら個別に削除すると、結構めんどくさいので、使ってないということもあって、もう一括でバケットごと空にする方向で。ほんとは、バケットに自動削除の指定をしておくのがいいのだよね。

　バケットにチェックを入れて、空にするボタンを押す。

![](/2024-10-18/8727020-03.png)

　確認が出るので「完全に削除」と入力して実行する。

![](/2024-10-18/8727020-04.png)

　削除作業中はブラウザを閉じられない感じ。バケットは２つあるので、別のタブで同じように空にする操作を行う。並列で問題ないようだ。記事にする予定がなかったので、スクショはない。

　あとは自動でよしなにやってくれると思ったら、オブジェクト数かサイズかよくわからないけど、しばらくすると削除が止まってしまう。数時間そのままにしても先に進まない。課金は続いてしまうのは困るので、一旦、空にする作業を終了して、再度やり直す感じ。

　これを繰り返すこと数回、二日ががりで、ようやくバケットが空っぽになった。

　CLIとかでやっても、途中で止まってしまうのだろうか？ ほんと困るわー。

　バージョニングがどうなっているか確認したら、デフォルトで有効になっているようだ。削除が遅いのはそういうこともあるのだろうな。

![](/2024-10-18/8727020-05.png)

　CloudShellから、CLIで確認してみる。

````text
$ aws s3api get-bucket-versioning --bucket aws-controltower-logs-XXXXXXXXXXXX-ap-northeast-1
{
    "Status": "Enabled"
}
````

````text
$ aws s3api get-bucket-versioning --bucket aws-controltower-s3-access-logs-XXXXXXXXXXXX-ap-northeast-1
{
    "Status": "Enabled"
}
````

　CLIからのバケットを空にするのは以下でよさそうだが、バージョニングが有効だと、この方法はダメらしい。

````text
aws s3 rm s3://バケット名 --recursive
````

　その場合はこっち。

````text
aws s3api delete-objects --bucket バケット名 --delete "$(aws s3api list-object-versions --bucket バケット名 --output=json --query='{Objects: Versions[].{Key:Key,VersionId:VersionId}}')"
```&#8203;:contentReference[oaicite:0]{index=0}&#8203;:contentReference[oaicite:1]{index=1}。
````

　どっちも試してないので注意。

　削除が終わっているかは、ストレージレンズでは現在の状況はすぐには確認できず、二日前くらいになるので、バケットメトリクスで確認する。削除されている。

![](/2024-10-18/8727020-06.png)

　ついでにライフサイクルルールを設定しておく。管理コンソールからであれば、バケットの「管理」タブにライフサイクルルールがある。デフォルトでもRetentionRuleが設定されている。

![](/2024-10-18/8727020-07.png)

　RetentionRuleの詳細を見ると、365日で削除するようになっている。なるほど、２年分たまっているわけではないのかな？

![](/2024-10-18/8727020-08.png)

　ちょっと長すぎる感じなので、三ヶ月にしておこう。編集ボタンを押して、日数を変更する。有効期限が切れているフラグと、削除の実行は別になっている。

![](/2024-10-18/8727020-09.png)

　保存ボタンを押して反映する。ここにチェックを入れておかないと保存できなかった。

![](/2024-10-18/8727020-10.png)

　すると、IAMのエラーで弾かれた。

![](/2024-10-18/8727020-11.png)

　SSOから管理者で入っているのだけどな... まぁ、証憑なので、このくらい厳しくていいとは思うよ。

　現在のIAM権限を確認する。

````text
$ aws sts get-caller-identity
{
    "UserId": "XXXXXXXXXXXXXXXXXXXXXXXX:demokinneko",
    "Account": "XXXXXXXXXXXX",
    "Arn": "arn:aws:sts::XXXXXXXXXXXX:assumed-role/AWSReservedSSO_AWSAdministratorAccess_XXXXXXXXXXXX/demokinneko"
}
````

　SSOから、AWSAdministratorAccessで入っているのだけどダメのようだ。AWSOrganizationsFullAccessでもダメらしい。

　やだなぁ、IAM権限を作ったりロールに権限を追加したりするのは、Log Arhiveの運用上いやなので、rootで変更するしかない感じ。でも、それも嫌だな...

　というわけで、ライフサイクルルールは放置で365日でよいということにしたw

　Logアカウント作成時って、なんか保持日数が選択できたような気もするけど、確認していない。（どうもなさそう...）
