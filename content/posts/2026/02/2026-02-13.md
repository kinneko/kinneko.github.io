　Super mini S3を使って、Secure Boot V2をテストしてみる。

　プロジェクトは動作確認に使ったsupermini_rgb48_testをそのまま使う。

　Secure Boot V2は、趣味のプロダクトをビルドするときには、まったく気にする必要がないのだけれど、商用の商品をリリースする場合には必須の項目になる。

　Secure Boot V2とは

　PCのブートプロセスほど厳格ではないけれど、マイコンであるESP32にもSecure Bootの仕組みがある。

　ドキュメントはこのあたり。

> Secure Boot v2 - ESP32-S3 - — ESP-IDF Programming Guide v5.5.2 documentation<br>
> <https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/security/secure-boot-v2.html>

　Secure Bootは、デバイス上で未署名・不正署名のコードを起動しないようにして、アプリケーションの改ざんや差し替えを防ぐ機能。

　ROM上にあるブートローダーである1st stage bootloaderが、eFuseに書かれた公開鍵のダイジェストを使って2nd stage bootloaderの署名ブロックの公開鍵のダイジェストが一致するかを検証し、さらに2nd stage bootloaderの署名検証を行う。2nd stage bootloaderは、アプリ側の署名ブロックに入っている公開鍵を使い、そのダイジェストがeFuse登録済みのものと一致することを確認した上で、その公開鍵を使ってアプリケーションイメージやOTAイメージの署名を検証して、マッチしない場合は起動しないようにする。

　ただ、アプリケーションなどに署名はされていても、eFuseに鍵が書き込まれ、Secure Boot V2を使用する設定になっていない場合は、署名がされたバイナリでも普通に起動できるので、署名そのものは開発の初期からやるように設定しておいたほうがよい。

　eFuseへの鍵のダイジェストの書き込みは、一度行うと書き換えができず、開発時には不自由な環境を強いられるため初期からやるべきではない。製品の製造や出荷時に行うのがよい。

　公開鍵のダイジェストを書き込むeFuse領域は３つあるので、未使用エリアをrevoke設定していない限り、ダイジェストは３種類保持することができる。署名検証の検索は順に行われるため、いずれかの鍵で署名されたイメージを起動することができる。

　このような機能は、鍵の漏洩時や漏洩リスクの低減などで、鍵ローテーションを行う場合に利用できる。アップデートで、アプリケーション側からもう使わない鍵のrevokeを行うことはできるが、起動不能になるリスクを伴うので、製造時の管理などで利用することを想定している。一度revokeしてしまうと、そのエリアは使用できなくなるので注意。

　Secure BootはV1とV2があって、検索して出てくる日本語での解説はV1についての内容がほどんどであり、V2とは状況が異なるのであまり参考にならないので注意。

　署名の実行-手動署名-

　作成した鍵を使って実際に署名を行うには、ビルド時に自動適用する方法と、ビルドしたバイナリにコマンドで署名を追加する方法がある。手動署名と自動署名の順で試す。

　署名する必要があるファイルは通常ビルドを行うと作成される以下の４つになる。

　・アプリとOTA：build/ota_data_initial.bin, build/supermini_rgb48_test.bin

　・ブートローダー(2nd)：build/bootloader/bootloader.bin

　・パーティションテーブル：build/partition_table/partition-table.bin

　ただし、パーティションテーブルの署名は検証されないので、手動で行う場合はやる必要はない。

　アプリ本体のsupermini_rgb48_test.binを署名してsupermini_rgb48_test_signed.binを作る。使用するコマンドはidf.py secure-sign-dataとespsecure.py sign_data --version 2があって、どちらかを実行する。

　idf.py secure-sign-dataの実行時には、内部でbuildが作業ディレクトリになるので、イメージのbuildパスは指定する必要がない、また、keyfileはbuildからの相対パスで指定しておく。(そんなん知らんがなめんどくさ)

　% idf.py secure-sign-data --keyfile ../keys/secure_boot_signing_key.pem --output supermini_rgb48_test_signed.bin supermini_rgb48_test.bin
